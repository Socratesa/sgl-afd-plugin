# PR-03：A↔F 传输库

范围：`python/sgl_asap_plugin/transport/`。只依赖 libcuda（ctypes）和 numpy，不依赖 sglang，torch 只在测试里用。还没有接进 scheduler：A 侧 RemoteMoE 是 PR-04，F 服务是 PR-05。

## 一条消息怎么走（A rank a，slot s，F rank f）

A 的流上依次排队，A 的 CPU 只入队，不等：

1. 反压：`wait32(done[f][s] >= seq-1)`。上一条消息的回复到了，才复用这个 slot 的缓冲。
2. 三次 `cuMemcpyAsync`（x、topk_ids、topk_w）写进 F 的 RecvArena（CUDA IPC 映射）。
3. 一次 `cuStreamWriteValue64`：把 doorbell 写进 F 的 /dev/shm 槽文件。它在同一个流里排在拷贝之后，带内存屏障，F 看到 doorbell 时数据已经完整。
4. `wait_combine`：对每个 F 排 `wait32(done[f][s] >= seq)`，结果在 `result_ptrs`（A 的设备内存）。

F 的 CPU 用普通 load 轮询槽文件。同一个 A 副本的 T 行都到齐后组成一个 `Job` 交给 handler，handler 算完调 `reply(row, src, nbytes, stream)`：把部分和拷进 A 的 ResultArena，再 `write32(done[f][s], seq)`。

等待不占 SM，也不占 CPU。F rank 之间没有通信，按到达顺序服务。

## doorbell（一个 64 位字）

| 位 | 字段 | 范围 |
|---|---|---|
| 0–31 | seq，同时是就绪标志 | u32，按 int32 差值比较，回绕安全 |
| 32–48 | n_tokens | 1 .. 131071 |
| 49–58 | layer_id | 0 .. 1023 |
| 59–63 | epoch | 1 .. 31，握手分配 |

`magic`、`hidden`、`topk`、`dtype`、容量等不随消息携带，握手时一次对齐：`PROTO_VERSION`（现为 2）或 `Geometry` 任一字段不一致就拒绝，错误信息指出字段。`n_max` 因此不能超过 131071，`config.MAX_N_MAX` 与之相同。

为什么是一个字而不是 64 B 的 header：主机内存到主机内存的 `cuMemcpyAsync` 会阻塞调用线程，直到同一个流上此前的操作全部完成，A 的 CPU 就被 F 卡住，"CPU 领先入队、GPU 靠流依赖等待"不成立（反压测试因此挂死）。一次 64 位 memop 立即返回，F 也不会读到"有标志、没元数据"的中间态。

## 布局 `Geometry(num_a, group, slots, n_max, hidden, topk, num_f)`

- F 的 RecvArena：区域 [a][s] = `x | topk_ids | topk_w`，各段 256 B 对齐。
- F 的槽文件：每个 [a][s] 占一个 64 B 缓存行，里面一个 doorbell 字。
- A 的 ResultArena：2 MiB 的 done 标志页（每个 [f][s] 一个缓存行），后面是部分和段 [f][s]。
- `layout.arena_plan` 直接用 `Geometry`，所以 `ffn_serve --asap-dry-run` 打印的就是实际分配的大小。D·T=4、S=2、n_max=16K、E=4：F 1,080,033,280 B，A 1,075,838,976 B。

done 标志页独占 2 MiB 是实测得出的。负载紧跟在标志后面 4 KiB 时，F→A 的拷贝只有 287 GB/s，发送与回复重叠的流水线 549 GB/s；隔开 64 KiB 及以上，分别是 384 GB/s 和 687 GB/s。原因没有查明。已排除：缓冲来自 torch 还是 cuMemAlloc、目的地址对齐、流的创建方式、doorbell 在设备内存还是主机内存及其位宽、torch 上下文、memop 屏障、A 和 F 两侧的 Python 代码。

## 连接、epoch、故障

- **握手**：F 监听 TCP（端口 0 取临时端口）。A 发 `{proto, a, geometry, result_handle}`，F 校验后回 `{epoch, recv_handle, shm_path, seq_base}`，双方 `cuIpcOpenMemHandle`。
- **epoch**：1..31，由 F 分配，重连时加 1 并循环。F 丢弃 epoch 不符的 doorbell 并计数（`stale_epoch`）。重连时 F 复位该 A 的 doorbell 和 `last_seen`，丢掉半组装的 job。
- **丢消息检测**：F 对每个 [a][s] 记 `last_seen`，`seq - last_seen` 大于 1 就计入 `lost_messages`。反压正常时恒为 0。
- **超时**：A 侧 watchdog 线程每 2 ms 扫一遍各组等待前后的 event。某组等待超过 `timeout_s`（默认 30 s），它从另一个流写入这些等待的目标值，把被 park 的流放出来，并把通道标为 `ChannelPoisoned`。此后 `send`、`check` 抛错，放出之后读到的结果是垃圾。恢复只有 `reconnect()`（新 epoch、新 ResultArena）。
- **F 的轮询**：`serve_forever(handler, stop, spin_s=5ms, idle_sleep_s=200us)`。最后一个 job 之后自旋 5 ms，再每轮小睡。一次 `sleep(200us)` 实际 253 us，会给下一个 doorbell 的发现平均加约 125 us（n=1 的 RTT p50 从 61 us 升到 187 us）。

## 调用方规则（PR-04、PR-05 要遵守）

- x、ids、w 在 send 的拷贝执行前不能改动，同一个流里的顺序即可保证。
- 一个 slot 的结果指针，必须在同一 slot 的下一次 send 之前（在流内）消费完：F 回复下一条消息时会覆盖它。
- 超时之后结果无效，使用结果前先 `check()`。
- 被 park 的等待会拖住冷路径（第一次启动的 kernel、`cudaMalloc` 等要设备级同步的操作），直到 F 回复才放行。`CUDA_MODULE_LOADING=EAGER` 无效。A 在服务请求前要把所有 kernel 预热、缓冲分配好。释放必须来自另一个进程：同进程释放会死锁。
- F 的 handler 不要在轮询线程里做长时间的 CPU 工作，否则 doorbell 的发现会被推迟。

一条命令：`python scripts/pr03_acceptance.py --gpus 0,1,2,3`。需要同一台机器上的 4 张 GPU（A 和 F 的每个 rank 都是独立进程）。每个检查对应 `tests/test_transport*.py` 里的测试，门限写在测试里。

| C2 | 乒乓，校验 x、ids、w 和 layer id | 1000 轮，0 错，0 丢 |

## 已知限制

- 单机，A、F 在同一台机器上：传输是 CUDA IPC 加 /dev/shm。
- MVP 全广播：每个 A 向每个 F 发整份 payload。
- payload 固定 bf16，hidden、topk 在 `Geometry` 里固定，没有逐条的 dtype 字段。
- seq 在入队时就固定了，CUDA graph 的 replay 不会让它前进。进 graph 要改成设备侧计数，属于 Final。
- epoch 只有 5 位（31 代）。循环后旧代的 doorbell 已在握手时被复位，不会被误认。
- 单个 F 进程的 CPU 轮询线程是串行的：doorbell 发现和 reply 入队都在它上面。
