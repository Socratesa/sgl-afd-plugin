# M0：架构骨架与验收

M0 只交付"地基"：能起来的 hook、可校验的配置、纯 DP 的 A 角色、F 角色的启动契约与静态布局、一键验收。传输、专家计算、A 侧 RemoteMoE 属于 M1。按要求，PR-01（基准与对齐 harness）、PR-02（F 专家吞吐曲线）暂缓。

| 在 M0 内 | 不在 M0 内（M1 起） |
|---|---|
| 插件骨架、两层 hook 装配、目标/签名预检、安装后自检 | A↔F 传输库（arena、flag、握手） |
| `--asap-*` 配置与环境导出 | A 侧占位 experts、RemoteMoE、权重过滤 |
| A、F 两个角色的启动期校验 | F 服务循环与专家前向 |
| F 入口的启动契约、专家划分、arena 大小计算 | dual-batch、length-aware、CUDA graph |
| 验收脚本和一个会失败的反例对照 | 基准 harness（PR-01）、吞吐曲线（PR-02） |

M0 的 A 服务跑的是 stock 模型（专家仍在本地），只验证"纯 DP 拓扑 + hook 生效 + 校验"；数据通路从 M1 开始替换。

## 校验规则

所有问题一次报全，消息指出应改的选项。

- **A（`validation.check_attn`）拒绝**：`--enable-dp-attention` / `--attn-dp-size>1`（会把副本耦合进每步 all-gather）、`--nnodes>1`（传输是 CUDA IPC，A、F 须同机）、`--pp-size>1`、`--moe-a2a-backend` 不是 none、`--ep-size>1`、`--enable-eplb`、`--expert-distribution-recorder-mode`、`--disaggregation-mode decode`（只做 prefill），以及与 `--dp-size` / `--tp-size` 不一致的 `--asap-num-replicas` / `--asap-replica-tp`。
- **F（`validation.check_ffn`）要求**：`--ep-size == --tp-size`（= E）、无 DP 与 attn-DP、a2a 为 none、单机、PP=1、不开 EPLB、`--disaggregation-mode null`。
- **F 的布局**（`layout.py`）：E 不整除专家数时补 dummy 专家（256 个专家：E=3 补到 258，E=5 补到 260，E=6 补到 258）；arena 大小与设计文档 `02b` §6 一致（D·T=4、S=2、n_max=16K、E=4：F 侧 1,080,033,792 B，A 侧 1,073,741,824 B）。

## 目录

```
python/sgl_asap_plugin/
  __init__.py      register()，入口点；保持零重依赖
  activation.py    何时、如何激活两层 hook；失败语义
  config.py        AsapConfig、--asap-* 选项、ASAP_* 环境往返
  compat.py        目标/签名预检、安装后自检、版本提示
  hooks/           HookSpec 表：cli.py（base）、validate.py、scheduler.py（role）
  validation.py    A、F 的规则（只读属性，可用 SimpleNamespace 单测）
  layout.py        专家划分、arena 大小、MoE 形状读取
  runtime.py       每个 scheduler 进程的 ASAP 身份
  ffn_serve.py     F 入口（M0：校验、布局、生命周期）
tests/             unittest；含"全新进程里装 hook"的子进程测试
scripts/           launch_attn_dsv4_tiny.sh、m0_acceptance.py（+ accept_lib / accept_server_checks）
```

## 新增一个 hook

1. 在 `hooks/<模块>.py` 写 hook 函数和 `HookSpec(target, fn, type, params, tier)`，`params` 写目标的前几个参数名，预检靠它发现签名漂移。
2. 把目标写进 README 的 hook 表（`tests/test_docs.py` 检查），并加进 `tests/test_hooks.py` 的 `BASE_TARGETS` / `ROLE_TARGETS`。
3. 跑 `python scripts/m0_acceptance.py`；`G1` 会核对每个进程里的 hook 数。

## 验收标准

| ID | 检查 | 通过标准 |
|---|---|---|
| U1 | 单元与全新进程 hook 测试 | ≥ 43 个用例，0 失败，0 跳过 |
| U2 | 入口点可被 sglang 发现 | `sglang.srt.plugins` 组里有 `sgl_asap_plugin:register` |
| U3 | 导入保持轻量 | `import sgl_asap_plugin` < 500 ms，且不引入 torch、sglang |
| G0 | A 服务（D=2、T=1，DSV4 截 4 层 dummy）启动 | 900 s 内 `/health` 返回 200。仅当日志出现 `EADDRINUSE` 时重试，最多 3 次，次数计入结果：sglang 的 DPC 用 `bind(0)` 选各副本的 rendezvous 端口后立即释放，本机临时端口范围是 10000–61000，释放到副本绑定之间可能被别的外连占用（与插件无关） |
| G1 | hook 在启动进程和每个 scheduler 进程都生效 | 启动进程有校验日志；恰好 D·T 行 scheduler 日志；每行 hooks 全部已应用 |
| G2 | 纯 DP：每个副本是独立 WORLD | dp_rank 集合 = {0,1}；每个 scheduler 的 world_size = tp_size = 1（不是 D·T = 2） |
| G3 | 副本能服务请求 | 定向每个副本 3 次 + 轮询 4 次，全部成功 |
| G4 | 副本独立性 | `SIGSTOP` 副本 0 后，副本 1 的 5 次请求全部成功且最慢 ≤ 10 s；发往副本 0 的请求 5 s 内无回复（实验有效）；`SIGCONT` 后副本 0 恢复服务 |
| N1 | 反例：stock attention-DP 下做同样实验 | 停掉一个 scheduler 后，两个 rank 都不再回复（G4 的判据确实能失败） |

## 已知限制

- 目标解析会在所有 sglang 进程里 import 对应模块（包括 DPC、detokenizer 里的 `scheduler` 模块），启动略慢；按进程类型裁剪 hook 留到有性能数据时再做。
- 只在 sglang 0.5.22（`baa9befa38`）上验证；其他版本由预检决定能否启动，并打印警告。
- 单机；跨机传输（NVSHMEM 等）属于 PR-18。
- `ffn_serve` 的 worker 是占位：只证明启动契约（就绪日志、SIGTERM 干净退出），没有传输和专家前向。
